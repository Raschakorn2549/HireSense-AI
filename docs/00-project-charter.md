# HireSense AI — Project Charter (Phase 0)

> เอกสารนี้คือ "สัญญากับตัวเอง" ว่าโปรเจคนี้จะทำอะไร ไม่ทำอะไร และจะรู้ได้ยังไงว่าสำเร็จ
> ทุกครั้งที่อยากเพิ่มฟีเจอร์ ให้กลับมาอ่านไฟล์นี้ก่อน
>
> สร้างเมื่อ: 2026-11-16 · สถานะ: Phase 0 (วางแผน) · ยังไม่มีโค้ด

---

## 1. เป้าหมายหลัก

แปลง resume PDF เป็นข้อมูลมีโครงสร้าง แล้วเทียบกับความต้องการของตำแหน่งงาน
**พร้อมชี้หลักฐานในเอกสารต้นฉบับ** โดยวัดความแม่นยำออกมาเป็นตัวเลขได้

เป้าหมายรองที่สำคัญไม่แพ้กัน: เจ้าของโปรเจคต้องอธิบายสถาปัตยกรรมและเหตุผลเบื้องหลัง
ทุกการตัดสินใจได้ด้วยตัวเอง

### บริบทการเรียนรู้

- **ไม่มีเส้นตาย** — เน้นความเข้าใจมากกว่าความเร็ว
- **สมดุลระหว่างเข้าใจลึกกับมีของเดโม** — ทุก phase ต้องจบด้วยของที่แสดงให้คนอื่นดูได้
- **ไม่มีงบสำหรับ LLM API** — ดูข้อ 6

---

## 2. สิ่งที่ระบบนี้ *ไม่* ทำ

การเขียนข้อนี้ให้ชัดสำคัญพอ ๆ กับการเขียนว่าทำอะไร เพราะมันคือสิ่งที่กัน scope creep

1. **ไม่ตัดสินใจรับ/ไม่รับแทนมนุษย์** — เป็นเครื่องมือช่วยตัดสินใจ (decision-support) เท่านั้น
2. **ไม่ให้คะแนนรวมเป็นตัวเลขเดียว** แบบ "ผู้สมัครคนนี้ 87 คะแนน" — เพราะตัวเลขเดียว
   ดูน่าเชื่อถือเกินความจริง และซ่อนที่มาของมัน ระบบจะแสดงเป็น *หลักฐานรายทักษะ* แทน
3. **ไม่เป็นระบบ ATS เต็มรูปแบบ** — ไม่มีนัดสัมภาษณ์ ไม่มีส่งอีเมลหาผู้สมัคร
4. **ไม่รองรับ resume ภาษาไทยในเวอร์ชันแรก** — ดูข้อ 5
5. **ไม่ใช้ข้อมูลบุคคลจริง** — ใช้ข้อมูลสังเคราะห์เท่านั้นตลอดการพัฒนา

## 3. ฟีเจอร์ แบ่งตามความสำคัญ

| ระดับ | ฟีเจอร์ |
|---|---|
| **ต้องมี (MVP)** | สร้าง job + ระบุ required/preferred skills<br>อัปโหลด PDF<br>สกัดข้อมูล: ชื่อ, อีเมล, เบอร์, การศึกษา, ประสบการณ์, ทักษะ<br>matching พร้อมหลักฐาน<br>รายการผู้สมัคร |
| **ควรมี** | สถานะผู้สมัคร (New / Under Review / Shortlisted / Interview / Hired / Not Selected)<br>ค้นหาและกรอง<br>dashboard กราฟ<br>LLM อธิบายผล |
| **ถ้ามีเวลา** | เทียบผู้สมัครหลายคนเคียงกัน<br>export รายงาน<br>รองรับ resume ภาษาไทย |
| **ไม่ทำในโปรเจคนี้** | authentication<br>role-based access control<br>multi-tenant |

> **หมายเหตุเรื่อง authentication:** ถูกตัดออกเพราะไม่ได้ทำให้โปรเจคน่าสนใจขึ้น
> ในสายตาคนสัมภาษณ์ตำแหน่ง AI และกินเวลามาก ถ้าภายหลังอยากเรียนเรื่องนี้จริง ๆ
> ให้ย้ายขึ้นมาเป็น "ถ้ามีเวลา" ได้ แต่อย่าทำก่อน MVP เสร็จ

## 4. เกณฑ์ความสำเร็จ

เกณฑ์ต้องเป็นตัวเลข ไม่ใช่ "มันทำงานได้"

| วัดอะไร | เป้า | วัดด้วยอะไร |
|---|---|---|
| สกัดอีเมล / เบอร์โทร ถูกต้องตรงเป๊ะ | ≥ 95% | dataset 20 resume (Phase 1) |
| สกัดทักษะ — F1 score เทียบเฉลยที่คนตรวจ | ≥ 0.80 | เฉลยที่ annotate เอง |
| จัดอันดับผู้สมัคร top-3 ตรงกับที่คนจัด | ≥ 70% | การจัดอันดับโดยมนุษย์ |
| ทุกทักษะที่ระบบบอกว่า "เจอ" ชี้กลับไปยังข้อความต้นฉบับได้ | 100% | ตรวจด้วยตา + test |
| เวลาตอบของ API (ไม่นับเวลาเรียก LLM) | < 2 วินาที | วัดใน test |

**กฎเหล็ก:** ตัวเลขเหล่านี้ตั้งไว้ *ก่อน* เขียนโค้ด ห้ามปรับลงทีหลังเพื่อให้พอดีกับผลที่ได้
ถ้าทำไม่ถึงเป้า ให้บันทึกไว้ว่าทำได้เท่าไรและเพราะอะไร — นั่นคือผลการทดลองที่มีค่า
ไม่ใช่ความล้มเหลว

## 7. ลำดับ Phase

**หลักคิด: ทำสิ่งที่ยังไม่รู้ว่าจะเวิร์กไหมก่อน** ส่วนที่รู้แน่ว่าทำได้ (CRUD, หน้าเว็บ) เอาไว้ทีหลัง

| Phase | ทำอะไร | ได้อะไรออกมา | ทักษะที่ได้ |
|---|---|---|---|
| **0** | นิยามเป้าหมาย ตัดสโคป เขียนเกณฑ์วัดผล | เอกสารนี้ | requirement analysis |
| **1** | สร้าง dataset สังเคราะห์ ~20 resume + 3 job + **เฉลยที่ตรวจเอง** | `dataset/` | data engineering, annotation |
| **2** | PDF → text → JSON มีโครงสร้าง (ทำใน notebook) | pipeline + ตัวเลข accuracy | NLP, regex, document parsing |
| **3** | matching 3 วิธี เทียบกัน วัดผลด้วย dataset จาก Phase 1 | ตารางเปรียบเทียบ | ML, evaluation |
| **4** | LLM ช่วยสกัดและอธิบายผล + validate JSON + วัดว่าดีขึ้นไหม | AI service | LLM engineering, prompt design |
| **5** | ออกแบบ schema + PostgreSQL + FastAPI | API ที่ใช้งานได้ | backend, database design |
| **6** | React UI + dashboard | เว็บที่เดโมได้ | frontend |
| **7** | Docker, deploy, README | ลิงก์ที่ส่งให้คนอื่นดูได้ | DevOps |

### ทำไมถึงไม่เรียงแบบเดิม (UI → parsing → ML → LLM → DB)

1. **Database อยู่ท้ายเกินไปในแผนเดิม** — ถ้าทำ parsing/ML/LLM โดยยังไม่มีที่เก็บข้อมูล
   โค้ดสามเฟสนั้นจะเก็บของไว้ชั่วคราว แล้วต้องกลับมารื้อใหม่
2. **UI อยู่ต้นเกินไปในแผนเดิม** — ออกแบบหน้า "โปรไฟล์ผู้สมัคร" ไม่ได้
   ถ้ายังไม่รู้ว่าดึงอะไรออกจาก PDF ได้บ้าง
3. **แผนเดิมไม่มี evaluation dataset เลย** — ซึ่งทำให้วัด Precision/Recall/F1 ไม่ได้

**Phase 2 และ 3 ทำใน Jupyter notebook ล้วน ๆ** ไม่มีเว็บ ไม่มี API ไม่มี database
เพราะเป็นหัวใจ AI ของโปรเจค และ notebook ทำให้ลองผิดลองถูกได้เร็วกว่ามาก
พอผลนิ่งแล้วค่อยห่อเป็น service ใน Phase 5

## 8. หลักความรับผิดชอบ (Responsible AI)

1. ผลลัพธ์ทุกอย่างต้องสืบกลับไปยังข้อความในเอกสารต้นฉบับได้
2. ห้ามใช้ลักษณะที่ได้รับการคุ้มครอง (เพศ อายุ ศาสนา เชื้อชาติ สถานภาพ) เป็นเกณฑ์จัดอันดับ
3. ห้ามปฏิเสธผู้สมัครอัตโนมัติจากคะแนนของ AI
4. AI ต้องแยกให้ออกระหว่าง "ไม่พบในเอกสาร" กับ "ไม่มีคุณสมบัติ" — สองอย่างนี้ต่างกัน
5. ห้ามแต่งคุณสมบัติหรือประสบการณ์ที่ไม่มีในเอกสาร
6. ข้อมูลส่วนบุคคลต้องไม่ถูก commit เข้า git และไม่ถูก log โดยไม่จำเป็น

## 9. ขั้นต่อไป

**Phase 1 — สร้าง evaluation dataset**

1. เขียน job description 3 ตำแหน่ง พร้อมระบุ required / preferred skills ให้ชัด
2. สร้าง resume สังเคราะห์ ~20 ใบ ให้มีความหลากหลาย (ตรงมาก / ตรงบางส่วน / ไม่ตรง / รูปแบบแปลก)
3. แปลงเป็น PDF
4. **annotate เฉลยด้วยตัวเอง**: resume แต่ละใบมีทักษะอะไรบ้าง และควรอยู่อันดับไหนของแต่ละตำแหน่ง

ขั้นตอนที่ 4 น่าเบื่อที่สุดและมีค่าที่สุด — มันคือสิ่งเดียวที่ทำให้ตอบคำถาม
*"รู้ได้ยังไงว่ามันแม่น"* ได้

## 10. บันทึกการแก้ไข

ข้อความต้นฉบับข้างบนถูกเก็บไว้ตามเดิมโดยเจตนา รายการด้านล่างคือสิ่งที่ถูกแทนที่ภายหลัง
พร้อมเหตุผล เพื่อให้ตามรอยการตัดสินใจย้อนหลังได้

| ข้อมูลสังเคราะห์ (§5) | profile → resume → PDF | **แยกฟิลด์ `identity` (ชื่อ/คำนำหน้า/สรรพนาม) ออกจาก `profile`** เพื่อ render เป็นคู่ counterfactual ได้ | ต้นทุนตอนนี้แทบไม่มี · ทำย้อนหลังต้องรื้อ profile pool ทั้งชุดเพราะชื่อฝังอยู่ในเนื้อหา resume ที่ render แล้ว | `02-dataset-strategy.md` §6.1 |
| ชุดข้อมูล (§9) | Tier A / B / C | **เพิ่ม smoke set 6 ใบ** ที่รู้ลำดับคำตอบอยู่แล้ว · ไม่ใช่ tier ใด · **ห้ามรายงานตัวเลขจากชุดนี้** | lockbox ห้ามแตะ Tier B ระหว่างพัฒนา และ Tier A ยังไม่มีในช่วงต้น → ไม่มีอะไรให้ยิงใส่ pipeline เลย | `02-dataset-strategy.md` §6.4 |
