## 1. หลักการ 5 ข้อ

1. **แยกงานวัด 2 งานเด็ดขาด** — Extraction (สกัดข้อมูล) กับ Matching (จับคู่งาน) ห้ามรวมเป็นคะแนนเดียว เพราะความล้มเหลวคนละสาเหตุและแก้คนละวิธี
2. **ตัวเลขทุกตัวผูกกับ `taxonomy_version`** — ถ้าแก้ taxonomy ตัวเลขเก่าเทียบกับใหม่ไม่ได้ ทุกผลการวัดต้องบันทึกเวอร์ชันไว้
3. **ห้ามใช้ LLM เป็น ground truth** — LLM เป็นสิ่งที่ถูกวัด ไม่ใช่ไม้วัด
4. **ไม่มีความต่างใดนับว่าเป็นการปรับปรุง จนกว่าจะเทียบกับ baseline แล้วช่วงความเชื่อมั่นไม่ทับกัน**
5. **เป้าหมายในเอกสารนี้ห้ามลดทีหลัง** — ทำไม่ถึงให้บันทึกว่าได้เท่าไรและเพราะอะไร นั่นคือผลการทดลอง ไม่ใช่ความล้มเหลว

## 2. ชุดข้อมูลที่ใช้วัด

| Tier | ที่มาของ label | เคลมอะไรได้ |
|---|---|---|

## 3. งานที่ 1 — Extraction

### 3.1 กฎ normalize (ต้องนิยามก่อนวัด ไม่ใช่ตอนวัด)

| ฟิลด์ | กฎ |
|---|---|
| **email** | ตัดช่องว่างหัวท้าย · แปลงเป็นตัวพิมพ์เล็กทั้งหมด · เทียบตรงทุกตัวอักษร |
| **phone** | เอาเฉพาะตัวเลข · ตัดรหัสประเทศ `66` หรือเลข `0` นำหน้าออก · เทียบ **9 หลักท้าย** |
| **name** | ยุบช่องว่างซ้ำเป็นช่องเดียว · ไม่สนตัวพิมพ์ใหญ่เล็ก · รายงาน 2 ตัวเลข: exact match และ token-set overlap |
| **skill** | map เป็น canonical id ก่อนเทียบ ไม่เทียบข้อความดิบ |
| **วันที่** | ความละเอียดระดับเดือน (`YYYY-MM`) |
| **ชื่อตำแหน่ง / นายจ้าง / สถาบัน** | normalize แล้วเทียบแบบ substring (ยอมให้ `Acme Co` ตรงกับ `Acme Co., Ltd.`) |
| **ข้อความยาว** (คำอธิบายงาน, คำอธิบายโปรเจค) | **edit-distance similarity ≥ 0.9** ไม่ใช้ exact match |

> **เพิ่ม 2026-11-18:** สองแถวล่างเป็นของใหม่ · v1 ไม่มีกฎรองรับฟิลด์ที่เป็นข้อความยาว
> ทำให้ถ้าระบบคาย `"Built REST APIs using FastAPI"` ขณะที่เฉลยเขียน `"Built REST API with FastAPI"`
> จะถูกนับผิดทั้งที่ความหมายเดียวกัน · เกณฑ์ 0.9 มาจาก `04-related-work.md` §2.1

### 3.2 Metric

**ข้อมูลติดต่อ (email, phone, name)**
accuracy แบบ exact match หลัง normalize · รายงานแยกแต่ละฟิลด์ ไม่รวมกัน

**ทักษะ**

```
TP = canonical id ที่อยู่ทั้งใน label และใน output
FP = อยู่ใน output แต่ไม่อยู่ใน label
FN = อยู่ใน label แต่ไม่อยู่ใน output
```

รายงาน **3 ชุด**:

| ชุด | ความหมาย | ทำไมต้องมี |
|---|---|---|
| **micro** P/R/F1 | รวมทุก mention เข้าด้วยกัน | ภาพรวม |
| **macro** P/R/F1 | เฉลี่ยค่าของแต่ละ skill id | ทักษะที่พบน้อยไม่ถูกทักษะยอดนิยมกลบ |
| แยกตาม **category** | language / framework / library / tool / platform / concept / soft | บอกว่าพังที่หมวดไหน |

> **กฎ uncertain:** รายการใน `skills_uncertain` ของ label ถูกตัดออกจากทั้ง TP, FP และ FN
> พร้อมรายงานจำนวนที่ตัดออกไปทุกครั้ง · ถ้าตัดออกเกิน 10% ของ mention ทั้งหมด
> แปลว่า annotation guidelines ยังไม่ชัดพอ ต้องกลับไปแก้ ไม่ใช่เดินหน้าต่อ

#### 🔴 ทักษะ — แยกให้ชัดว่ากำลังวัด 2 เรื่องคนละเรื่อง (เพิ่ม 2026-11-18)

v1 มีทั้งเกณฑ์ "สกัดทักษะได้ถูก" (§3.2) และเกณฑ์ "ชี้หลักฐานกลับต้นฉบับได้ 100%" (ท้าย §3.2)
แต่เอาไปรวมเป็นเรื่องเดียวกัน · **มันคนละเรื่อง และโมเดลพังได้ทีละเรื่อง**
ระบบอาจรู้ว่า resume ใบนี้มี `fastapi` (ถูก) แต่ชี้ไปที่บรรทัดผิด (ผิด) — v1 จับไม่ได้

ตั้งแต่ v1.1 ต้องรายงาน **3 ระดับ** ทุกครั้ง:

| ระดับ | นิยาม | เป็นตัวหลักของ |
|---|---|---|
| **Concept-level P/R/F1** | เทียบ **เซตของ canonical id** ตามสูตร TP/FP/FN ข้างบน · ไม่สนว่าชี้ไปที่ตำแหน่งไหน | เป้า micro F1 ≥ 0.80 / macro ≥ 0.65 (§3.3) — **นี่คือสิ่งที่ v1 วัดอยู่แล้ว** |
| **Exact-span F1** | นับเป็น TP เฉพาะเมื่อ canonical id ถูก **และ** `(start, end)` ตรงกับ span ของเฉลยทุกตัวอักษร | รายงานประกอบ ไม่ตั้งเป้า |
| **Relaxed-span F1 (IoU ≥ 0.5)** | นับเป็น TP เมื่อ id ถูก และ span ซ้อนทับเฉลยด้วย `IoU = \|∩\| / \|∪\| ≥ 0.5` | รายงานประกอบ ไม่ตั้งเป้า |

**ทำไม exact/relaxed ยังไม่ตั้งเป้า:** label ใน `03` §8.1 ตอนนี้ไม่ได้เก็บ span ของเฉลย
จึงยังคำนวณสองตัวล่างไม่ได้ · ถ้าจะเก็บ span ต้องเพิ่มงาน annotate ซึ่งยังไม่ตัดสินใจ (§10 ข้อ 5)
→ **ระหว่างนี้ exact/relaxed รายงานบน Tier A ได้** เพราะ generator รู้ตำแหน่งที่ใส่ข้อความลงไป
และนั่นก็เพียงพอต่อการจับบั๊ก off-by-one ของตัวชี้ span

> **กับดักที่ต้องระวัง (จาก `04-related-work.md` §4.1):** state of the art ของงาน span-level
> skill extraction ได้ strict F1 ราว **0.49–0.65** ขณะที่เราตั้งเป้า concept-level micro F1 ที่ 0.80
> สองตัวเลขนี้ไม่ขัดกันเพราะคนละงาน (ของเราไม่ต้องหาขอบ span, taxonomy ปิด, ข้อมูลสังเคราะห์)
> **แต่ถ้า exact-span F1 ของเราออกมา ≥ 0.80 ให้ถือเป็นสัญญาณว่า dataset ง่ายเกินไป**
> ไม่ใช่สัญญาณว่าระบบเก่ง → ไปตรวจ §6.2 ของ `02` ว่าความหลากหลายพอหรือยัง

**การศึกษา**

| ฟิลด์ | วิธีเทียบ |
|---|---|
| ระดับวุฒิ | exact จากรายการปิด (`high_school` / `vocational` / `bachelor` / `master` / `phd`) |
| สาขา | token overlap ≥ 0.8 |
| สถาบัน | exact หลัง normalize |
| ปีจบ | exact |

**ประสบการณ์ทำงาน**

จับคู่ตำแหน่งด้วย (ชื่อตำแหน่ง + นายจ้าง) แบบ fuzzy แล้วรายงาน:
- P/R/F1 ของจำนวนตำแหน่งที่ตรวจพบ
- ความแม่นของช่วงวันที่ — ถือว่าถูกถ้าคลาด **ไม่เกิน ±1 เดือน**

> **เพิ่ม 2026-11-18 — วิธีจับคู่ต้องนิยามให้ชัด ไม่ใช่แค่คำว่า "fuzzy":**
> 1. สร้าง similarity matrix ขนาด M×N (M = ที่ระบบคาย, N = ที่เฉลยมี)
>    แต่ละช่อง = ค่าเฉลี่ยความคล้ายของ (ชื่อตำแหน่ง, นายจ้าง) หลัง normalize
> 2. หาการจับคู่หนึ่งต่อหนึ่งที่ผลรวมความคล้ายสูงสุดด้วย **Hungarian algorithm**
>    (`scipy.optimize.linear_sum_assignment`)
>
> เหตุผล: ถ้าจับคู่แบบ greedy ตามลำดับ ผลจะเปลี่ยนตามลำดับที่ระบบคายออกมา
> ซึ่งทำให้ตัวเลขไม่นิ่ง · และ resume จำนวนไม่น้อยเรียงประสบการณ์คนละทิศกัน
>
> **และต้องรายงาน 2 ตัวแยกกัน:**
>
> | ตัว | สูตร | บอกอะไร |
> |---|---|---|
> | **F1** | จาก TP/FP/FN ปกติ | ภาพรวม |
> | **Accuracy** | `ถูก / จับคู่ได้` | เมื่อจับคู่ entity ถูกแล้ว ค่าในฟิลด์ยังผิดอีกเท่าไร |
>
> ถ้า F1 ต่ำแต่ Accuracy สูง → ปัญหาอยู่ที่ **การแบ่ง section / นับจำนวนตำแหน่ง**
> ถ้าทั้งคู่ต่ำ → ปัญหาอยู่ที่ **การอ่านค่าในฟิลด์** · สองอย่างนี้แก้คนละที่
> (ที่มา: `04-related-work.md` §2.1)

**Evidence traceability (ตรวจอัตโนมัติได้ 100%)**
ทุกรายการที่ระบบสกัดออกมาต้องมี `(start, end)` ชี้ไปยังข้อความต้นฉบับ
สคริปต์ตรวจว่า `text[start:end]` มีข้อความที่อ้างจริงหรือไม่
→ **metric = % ของรายการที่ตรวจผ่าน · เป้า 100%**
ข้อนี้ไม่ต้องใช้ label มนุษย์เลย ตรวจได้ตั้งแต่วันแรก

#### 🔴 Evidence contract — เป้า 100% จะเป็นจริงได้ด้วยการออกแบบ ไม่ใช่ด้วยการตรวจทีหลัง (เพิ่ม 2026-11-18)

v1 บอกว่า "ต้องชี้กลับได้ 100%" แต่ไม่ได้บอกว่า **ถ้าชี้ไม่ได้แล้วจะเกิดอะไรขึ้น**
ถ้าปล่อยไว้ เป้า 100% จะกลายเป็นตัวเลขที่ไม่เคยถึง แล้วค่อย ๆ ถูกยอมให้เป็น 97%
สามข้อนี้จึงเป็น **ข้อบังคับของ output ไม่ใช่ metric**:

| # | กฎ | ผล |
|---|---|---|
| 1 | **ทุกช่องทางการสกัด (regex, ML, LLM) ต้องคายตำแหน่งในเอกสาร ไม่ใช่คายข้อความ** — สำหรับ LLM ให้คาย **ช่วงเลขบรรทัด** ของข้อความที่ถูก index มาแล้ว แล้ว post-processor ไปดึงข้อความจริงตามเลขบรรทัดนั้น | ทำให้การแต่งข้อความเป็นไปไม่ได้ในทางเทคนิค ไม่ใช่แค่ถูกห้าม |
| 2 | **รายการที่ verify กับต้นฉบับไม่ได้ → สถานะ `unverified` และถูกตัดออกจากการคิดคะแนน matching** ไม่ใช่แค่ไม่แสดงผล | คะแนนจะไม่มีส่วนที่มาจากหลักฐานที่พิสูจน์ไม่ได้เลย |
| 3 | **ต้องรายงานจำนวน `unverified` ทุกครั้งที่รายงานคะแนน** | ถ้าตัวเลขนี้ไม่ใช่ 0 แปลว่ากฎข้อ 1 มีรูรั่ว ต้องไปแก้ที่กฎข้อ 1 |

ข้อ 1 มาจาก `04-related-work.md` §2.1 · ข้อ 2 มาจาก §5.3.2 ซึ่งเป็นคนละทีมกัน
และกฎเดียวกันนี้ไปปิดช่องเรื่อง LLM แต่งคุณสมบัติ (charter §8.5) ไปในตัว

> **ของแถม:** กฎข้อ 1 ทำให้ `inferred: true` (`03` §4.2) มีที่อยู่ที่ชัดเจน —
> ทักษะที่ได้จากการอนุมานไม่มี span จริง จึงต้องอยู่ในหมวดแยกโดยธรรมชาติ
> ไม่ใช่เพราะเราตั้งกฎไว้เฉย ๆ

### 3.3 เป้า

| วัดอะไร | เป้า | ที่มา |
|---|---|---|
| email exact | ≥ 95% | charter §4 |
| phone exact | ≥ 95% | charter §4 |
| skill micro F1 | ≥ 0.80 | charter §4 |
| skill macro F1 | ≥ 0.65 | ใหม่ — macro ต่ำกว่า micro เสมอ ตั้งเท่ากันคือการตั้งเป้าที่ทำไม่ได้ |
| evidence traceability | 100% | charter §4 |
| เวลาต่อ resume (ไม่นับ LLM) | < 2 วินาที | charter §4 |
| จำนวน `unverified` ในผลที่คิดคะแนน | **0** | ใหม่ 2026-11-18 · เป็นผลที่ตามมาจาก evidence contract ข้อ 2 |
| counterfactual invariance | **100%** | ใหม่ 2026-11-18 · ดู §11 |
| exact-span F1 / relaxed-span F1 | **รายงาน ไม่ตั้งเป้า** | ใหม่ 2026-11-18 · ยังไม่มี span ในเฉลย Tier B |

> **หมายเหตุเรื่องเป้า < 2 วินาที:** มีหลักฐานภายนอกว่าตั้งไว้สมเหตุสมผล —
> `04-related-work.md` §5.3.1 รายงานว่า rule-based scoring ให้คะแนน resume 1 ใบ
> เทียบตำแหน่งงาน 800 ตำแหน่ง ใน ~0.7 วินาที ส่วน end-to-end จาก PDF จริงอยู่ที่ ~4.5 วินาที
> (ซึ่งรวมเวลา LLM ที่เป้าของเราไม่นับ) → เป้าเราไม่ตึงเกิน แต่ก็ไม่หลวมจนไร้ความหมาย

## 4. งานที่ 2 — Matching / Ranking

### 4.1 รูปแบบ label

ต่อ 1 ตำแหน่ง ให้ความเกี่ยวข้องแบบมีระดับ **0–3** กับผู้สมัครทุกคนในชุด
(rubric อยู่ใน `03-annotation-guidelines.md` §6)

ไม่ใช้การเทียบเป็นคู่ (pairwise) เพราะ 30 คน = 435 คู่ ทำไม่ไหว

### 4.2 🔴 จำนวนตำแหน่งงาน — เรื่องที่ต้องเปลี่ยนจากแผนเดิม

Charter เดิมวางไว้ **3 ตำแหน่ง** ซึ่ง **ไม่พอสำหรับการวัด ranking**

เหตุผล: metric ของ ranking (NDCG, P@K) คำนวณ **ต่อ query** แล้วเฉลี่ย
ช่วงความเชื่อมั่นจึงมาจากความแปรปรวนระหว่าง query
**ถ้ามี 3 query ช่วงความเชื่อมั่นจะกว้างจนเทียบวิธีไหนก็ไม่ต่างกันทั้งหมด** —
ไม่ว่าจะมีผู้สมัครกี่คนก็ช่วยไม่ได้ เพราะผู้สมัครไม่ใช่หน่วยของการสุ่ม

| ทางเลือก | ผล |
|---|---|
| 3 ตำแหน่ง | สรุปทางสถิติไม่ได้เลย · ได้แค่รายงานแยกทีละตำแหน่ง |
| **6 ตำแหน่ง** ← เสนอ | เริ่มสรุปได้ (ยังหลวม แต่ซื่อสัตย์) · ต้น annotate 6 × 30 = **180 judgment ≈ 3 ชั่วโมง** |
| 10+ ตำแหน่ง | ดีทางสถิติ · แพงเกินสำหรับคนเดียว |

**✅ ตัดสินใจแล้ว 2026-11-17: ใช้ 6 ตำแหน่ง**

| Metric | นิยามที่ใช้ |
|---|---|
| **NDCG@10** | gain = `2^grade − 1` (grade 0–3) · ตัวหลัก |

## 5. ความเข้มงวดทางสถิติ

### 5.1 Bootstrap confidence interval

สุ่ม query ใหม่แบบมีการแทนที่ 1,000 รอบ → รายงานค่ากลางพร้อมช่วง 95%

**กฎการตีความ:** ถ้าช่วงความเชื่อมั่นของสองวิธีทับกัน ให้สรุปว่า **"แยกไม่ออกด้วยข้อมูลชุดนี้"**
ห้ามเขียนว่าวิธีหนึ่งดีกว่า

> ความผิดพลาดที่พบบ่อยที่สุดใน portfolio ML คือการรายงาน "0.81 ดีกว่า 0.79"
> จากข้อมูลไม่กี่สิบตัวอย่าง ข้อนี้มีไว้กันเรื่องนั้นโดยเฉพาะ

### 5.2 เพดานมนุษย์ (human ceiling)

ไม่มีผู้ annotate คนที่สอง → ใช้ **test–retest ของตัวเอง**

1. เลือก 10 resume จาก Tier B
2. annotate รอบสองหลังจากรอบแรก **ไม่น้อยกว่า 14 วัน** และไม่ดูของเดิม
3. คำนวณ: ความสอดคล้องของเซตทักษะ (Jaccard / F1 ของตัวเองเทียบตัวเอง) และ Spearman ของเกรด ranking

ตัวเลขนี้คือ **เพดาน** ผลของโมเดลต้องรายงานเทียบเพดานนี้ ไม่ใช่เทียบ 1.0

หลักฐานภายนอกประกอบ: CareerCorpus รายงานความสอดคล้องระหว่างผู้เชี่ยวชาญ 2 คน
ที่ Pearson **0.35–0.89** แล้วแต่หมวดอาชีพ → งาน ranking ผู้สมัครมีเพดานต่ำจริงในวงกว้าง
ไม่ใช่แค่กับเรา

**หลักฐานเพิ่มเติม 2026-11-18 — เพดานอาจต่ำกว่าที่คิดอีกมาก:**

| แหล่ง | ตัวเลข | สถานะ |
|---|---|---|
| งานที่ให้คน 3 คน annotate การคัดกรอง resume | Fleiss' kappa **0.167** (binary) / **0.122** (3 คลาส) → ผู้เขียนปฏิเสธที่จะถือว่า annotator คนใดคนหนึ่งเป็น ground truth | ⚠️ จาก snippet ยังไม่ได้อ่าน full text |
| งานฝั่ง IR เรื่องการให้คะแนน relevance สเกล 0–4 | ผู้ตรวจ 2 คนให้คะแนนตรงกันเป๊ะเพียง **42%** และเตือนว่าเมื่อโมเดลชนเพดานของ label แล้ว benchmark จะหยุดแยกความต่างได้ | ⚠️ เช่นกัน |

→ รายละเอียดใน `04-related-work.md` §6.3

**ผลที่ตามมาต่อการตีความผลของเรา:**

1. **ข้อจำกัดที่ต้องเขียนในรายงานตรง ๆ:** เรามี annotator คนเดียว · test–retest วัดได้แค่
   *ความสม่ำเสมอของคนคนนั้น* (intra-annotator) **ไม่ใช่** *ความถูกต้องของเกณฑ์* (inter-annotator)
   ค่าที่ได้จะสูงกว่าความจริงเสมอ เพราะคนเดียวกันมีอคติชุดเดียวกันทั้งสองรอบ
   → ห้ามเรียกค่านี้ว่า "เพดานมนุษย์" เฉย ๆ **ให้เรียกว่า "เพดานจาก test–retest ของผู้ annotate คนเดียว"**
2. 🔴 **ถ้า Spearman ของเกรด ranking ในรอบ retest ออกมาต่ำ ให้ถือว่าปัญหาอยู่ที่ rubric ไม่ใช่ที่ตัวคน**
   → กลับไปแก้ `03-annotation-guidelines.md` §6.2 ให้เกณฑ์แยกเกรดคมขึ้น **แล้ว annotate ranking ใหม่**
   ห้ามเดินหน้าด้วยเฉลยที่ตัวเองทำซ้ำไม่ได้ · เหตุผล: ถ้าเฉลยไม่นิ่ง ทุกตัวเลขหลังจากนั้นวัดความมั่ว
   ของเฉลย ไม่ได้วัดระบบ

🔶 *ถ้าภายหลังหาคนที่สองมา annotate ได้แม้แค่ 10 ใบ ให้เปลี่ยนมาใช้ค่าระหว่างผู้ annotate
แทน test–retest ทันที เพราะน่าเชื่อถือกว่า*

## 6. การประเมิน LLM (Phase 4)

| วัดอะไร | วิธี |
|---|---|
| **JSON validity rate** | % ของคำตอบที่ผ่าน Pydantic schema ในครั้งแรก |
| **Faithfulness / hallucination rate** | ทุกข้อความในคำอธิบายต้องอ้าง evidence id ที่มีอยู่จริง → **% ข้อความที่อ้างไม่ได้ = hallucination rate** ตรวจอัตโนมัติ |
| **การยอมรับว่าไม่รู้** | สร้างเคสที่ข้อมูลไม่มีในเอกสารโดยเจตนา → ต้องตอบ "ไม่พบในเอกสาร" ไม่ใช่เดา |
| ส่วนเพิ่มจาก baseline | เทียบ F1 / NDCG กับวิธี 1–4 ด้วย bootstrap CI |
| latency | วินาทีต่อ resume |
| cost | token ต่อ resume (รวม local model: เวลา + RAM) |

**ข้อห้าม:** ห้ามนำคะแนนหรือการจัดอันดับจาก LLM มาใช้เป็น ground truth
ห้ามให้ LLM ประเมินผลงานของ LLM โดยไม่มีมนุษย์ตรวจ

### 6.1 กฎการรันซ้ำ และความแปรปรวนของ LLM (เพิ่ม 2026-11-18)

v1 ไม่ได้พูดถึงเลยว่า LLM ให้คำตอบไม่เหมือนกันทุกครั้ง ซึ่งทำให้ตัวเลขทุกตัวในตารางข้างบน
กลายเป็นค่าที่วัดครั้งเดียวแล้วบังเอิญได้เท่านั้น

| กฎ | รายละเอียด |
|---|---|
| **ตั้ง `temperature = 0` และบันทึก seed (ถ้า provider รองรับ)** | ลดความแปรปรวนให้น้อยที่สุดก่อน แต่ไม่ถือว่าหายไป |
| **ทุก metric ของ Phase 4 ต้องรัน ≥ 3 รอบ แล้วรายงาน ค่ากลาง ± SD** | ตัวเลขรอบเดียวห้ามใส่ในรายงาน |
| **ถ้า SD กว้างกว่าส่วนต่างระหว่างวิธี → สรุปว่าแยกไม่ออก** | กฎเดียวกับ §5.1 |
| **บันทึก `provider` + ชื่อรุ่น + วันที่ทุกครั้ง** | โมเดลเดียวกันคนละวันให้ผลคนละอย่างได้ |

> **หลักฐานว่าเรื่องนี้สำคัญจริง:** JobResQA (`04-related-work.md` §3.3) วัดด้วย LLM-as-judge
> แล้วได้ SD สูงถึง **0.39** บนสเกล 0–1 — กว้างกว่าส่วนต่างระหว่างโมเดลหลายคู่ในตารางของเขาเอง
> ⚠️ *(ตัวเลขนี้มาจาก full text ของเปเปอร์ แต่เรายังไม่ได้ตรวจวิธีคำนวณของเขา)*

**เส้นอ้างอิงสำหรับเลือก provider (ยังไม่ใช่การตัดสินใจ — charter §6 ยังเปิดอยู่):**
JobResQA วัด Llama 3.3 70B บนงานอ่าน resume/JD ภาษาอังกฤษได้ **0.73** (สเกล 0–1)
และมี portfolio project ที่ใช้ Llama 3.3 70B ผ่าน Groq free tier ทำงานนี้ได้จริง
(`04-related-work.md` §5.3.4) → **เป็นตัวเลือกตั้งต้นที่มีหลักฐาน ไม่ใช่การเดา**
แต่ตัวเลข 0.73 เป็นงาน QA ไม่ใช่งานสกัดของเรา จึงใช้เป็นเส้นอ้างอิงคร่าว ๆ เท่านั้น

## 8. มาตรการป้องกัน Data Leakage

| ความเสี่ยง | มาตรการ |
|---|---|
| resume ซ้ำข้ามชุด | manifest เก็บ SHA-256 ของทุกไฟล์ + ชุดที่สังกัด · test ยืนยันไม่มี hash ซ้ำ 2 ชุด |
| template เดียวกันทำให้ผลดูดีเกินจริง | Tier A ใช้ template T1–T3 · Tier B ใช้ **T4–T5 ที่ไม่เคยใช้** |
| สร้างจาก pool เดียวกัน | profile pool (ชื่อ, นายจ้าง, ชุดทักษะ, seed) ต้องไม่ทับกันข้ามชุด |
| near-duplicate ที่ hash จับไม่ได้ | TF-IDF cosine ทุกคู่ข้ามชุด · เกิน threshold → เอาออกจาก Tier B |
| เผลอ tune บน eval | **lockbox** ดูข้อ 8.1 |
| เปิดดูตัวอย่าง eval เพื่อ debug | ตัวอย่างนั้น **ไหม้** → ย้ายไป Tier A ถาวร บันทึกไว้ |

### 8.1 Lockbox protocol

1. งาน debug, ลองพรอมต์, ปรับ regex, จูน threshold — **ทำบน Tier A เท่านั้น**
2. รัน Tier B ได้เฉพาะ **ตอนจบ phase** หรือเมื่อ baseline ใหม่พร้อมแล้ว
3. ทุกการรันบันทึกใน `docs/eval-runs.md` แบบ **เพิ่มได้ แก้ไม่ได้ ลบไม่ได้**:
   วันที่ · git commit · taxonomy_version · วิธีที่รัน · ผลทุก metric
4. **กัน 10 ใบเป็น final holdout** แตะครั้งเดียวตอนจบโปรเจค
5. จำนวนครั้งที่รัน Tier B ต้องรายงานในผลงานสุดท้าย — ยิ่งรันมากยิ่งเสี่ยง overfit โดยไม่รู้ตัว

## 11. 🔴 งานที่ 3 — Fairness (counterfactual invariance)

> **เพิ่ม 2026-11-18** · v1 ไม่มีส่วนนี้เลย ซึ่งเป็นช่องว่างที่ใหญ่ที่สุดของ v1

### 11.1 ปัญหาของ v1

charter §8.2 ห้ามใช้ลักษณะที่ได้รับการคุ้มครอง (เพศ อายุ ศาสนา เชื้อชาติ สถานภาพ) เป็นเกณฑ์จัดอันดับ
และ `03` §6.3 ห้ามไว้ในระดับการ annotate ด้วย

**แต่ทั้งสองที่เป็นข้อห้าม ไม่ใช่การวัด** — เราไม่มีวิธีพิสูจน์ว่าระบบทำตามจริง
ข้อห้ามที่ไม่มีการวัดกำกับคือความตั้งใจดี ไม่ใช่หลักประกัน และตอบคำถามสัมภาษณ์ไม่ได้

### 11.2 Metric

**นิยาม:** สำหรับ resume ทุกคู่ `(R, R′)` ที่เนื้อหาเหมือนกันทุกตัวอักษร
ยกเว้นชื่อ คำนำหน้า และสรรพนาม — ผลลัพธ์ของระบบต้องเหมือนกันทุกตัว

| ตัววัด | นิยาม | เป้า |
|---|---|---|
| **score invariance** | `% ของคู่ที่คะแนน matching เท่ากันทุกหลัก` | **100%** |
| **rank invariance** | `% ของคู่ที่อันดับในตำแหน่งเดียวกันไม่เปลี่ยน` | **100%** |
| **extraction invariance** | `% ของคู่ที่เซตทักษะที่สกัดได้เหมือนกัน` | **100%** |
| **explanation divergence** (Phase 4) | ความต่างของคำอธิบายที่ LLM เขียนให้คู่เดียวกัน | รายงาน · ยังไม่ตั้งเป้า |

### 11.3 ทำไม 3 ตัวแรกตั้งเป้า 100% ได้โดยไม่โลกสวย

เพราะคะแนนของเราเป็น **deterministic** และไม่รับชื่อเป็น input (§12)
→ ถ้าไม่ได้ 100% แปลว่า **มีบั๊ก** ไม่ใช่แปลว่า "โมเดลมีอคติเล็กน้อย"
นี่คือเป้าที่ผ่านง่ายจนน่าจะไร้ประโยชน์ **ตลอด Phase 2–3** และกลายเป็นเป้าที่มีความหมายทันที
ที่ LLM เข้ามาเกี่ยวใน Phase 4 — ซึ่งเป็นเหตุผลที่ต้องเริ่มวัดตั้งแต่ Phase 2
จะได้รู้ว่าตัวเลขก่อน LLM เป็นเท่าไร

### 11.4 ตัวที่ 4 ต่างจากสามตัวแรกอย่างสำคัญ

งานปี 2026 (`04-related-work.md` §6.2) รายงานว่าเมื่อให้ LLM สรุป resume
**เนื้อหาข้อเท็จจริงแทบไม่เปลี่ยนตามชื่อ แต่ภาษาที่ใช้ประเมินเปลี่ยน**
และความต่างไปกระจุกอยู่ที่ปลายการแจกแจง จึงรอดการ audit แบบดูค่าเฉลี่ย ⚠️

→ แปลว่า **ถ้าเราวัดแค่คะแนน เราจะประกาศว่า "ไม่มีอคติ" โดยที่คำอธิบายมีอคติอยู่**
สำหรับ Phase 4 จึงต้องเก็บคำอธิบายของทั้งคู่ไว้ **และอ่านด้วยตาอย่างน้อย 10 คู่**
ยังไม่ตั้งเป้าเป็นตัวเลข เพราะยังไม่มีวิธีวัดที่เชื่อถือได้ในกำลังของเรา
— การยอมรับว่าวัดไม่ได้แต่ไม่มองข้าม ซื่อสัตย์กว่าการแต่งตัวเลขขึ้นมา

### 11.5 ข้อจำกัดที่ต้องเขียนในรายงาน

counterfactual ตอบได้แค่ว่า **"ระบบไม่ได้ใช้ชื่อเป็นเกณฑ์"**
มันตอบ **ไม่ได้** ว่าทักษะ สำนวนการเขียน หรือชื่อนายจ้างในข้อมูลสังเคราะห์ของเรา
มีความสัมพันธ์กับกลุ่มที่ได้รับการคุ้มครองในโลกจริงหรือไม่ — ข้อมูลสังเคราะห์ตอบคำถามนั้นไม่ได้เลย
และงานปี 2026 อีกชิ้นเตือนว่า **ผลของการ audit ขึ้นกับวิธี audit เองไม่น้อยกว่าขึ้นกับตัวโมเดล** ⚠️

→ ห้ามเคลมว่า "ระบบนี้ fair" · เคลมได้แค่ว่า **"ผ่านการทดสอบ counterfactual ตามขอบเขตที่ระบุไว้"**

**ข้อจำกัดเพิ่ม (2026-11-18 รอบ 2):** การทดสอบนี้ครอบคลุมเฉพาะชื่อที่อยู่ในบล็อกหัวกระดาษ (§11.6)
resume จริงอาจมีชื่ออยู่นอกหัวกระดาษได้ เช่น ใน URL ของ LinkedIn / GitHub หรือในหัวข้อ References
ซึ่งการตัดบล็อกหัวกระดาษไม่ได้ป้องกันไว้ ต้องเขียนข้อนี้ในรายงานด้วย

### 11.6 กฎการตัดบล็อกหัวกระดาษ (เพิ่ม 2026-11-18 รอบ 2)

**ปัญหา:** §11.3 บอกว่า "ถ้าไม่ได้ 100% แปลว่ามีบั๊ก" เพราะระบบไม่รับชื่อเป็น input
แต่ baseline 3 (TF-IDF) และ 4 (Sentence Transformers) **อ่านข้อความ resume ทั้งก้อน**
ชื่อและอีเมลจึงเป็นคำใน input ด้วย → คะแนนขยับตามชื่อ **ไม่ใช่เพราะบั๊ก แต่เพราะชื่ออยู่ใน input จริง**
ถ้าไม่แก้ เป้า 100% จะล้มกับสอง baseline นี้ และคำอธิบาย "แปลว่ามีบั๊ก" จะผิด

**กฎ:**

1. identity (ชื่อ คำนำหน้า สรรพนาม อีเมล) อยู่ใน **บล็อกหัวกระดาษเท่านั้น** (`02` §6.1)
2. pipeline ต้อง **ตัดบล็อกหัวกระดาษออกก่อนส่งให้ matching ทุกวิธี** — รวม baseline ที่อ่านข้อความ
3. บล็อกหัวกระดาษยังถูกสกัดตามปกติเพื่อวัด extraction ของ email / phone / name (§3)
   แค่ไม่ถูกส่งต่อให้ matching
4. ด้วยกฎ 1–3 คำอธิบาย §11.3 ยังถูกต้อง: **ไม่ได้ 100% = มีบั๊ก** (เช่น ตัดบล็อกพลาด)
