# ANNOTATION GUIDELINES

> คู่มือ label ข้อมูลของ HireSense AI
> สร้าง: 2026-11-17 · แก้ไข: 2026-11-18 (v1.1) · 2026-11-24 (v1.2) · สถานะ: รออนุมัติ · **ยังไม่ผ่านการ pilot**
> สิ่งที่เปลี่ยนใน v1.1 และ v1.2 สรุปอยู่ใน §12 · label ที่จะทำต่อจากนี้ใช้ `guidelines_version: 1.2`
>
> คู่มือนี้จะถูกแก้หลัง pilot 5 ใบ (§10) ทุกครั้งที่แก้ให้ขึ้นเวอร์ชันและบันทึกว่าแก้อะไร
> เพราะ label ที่ทำด้วยคู่มือต่างเวอร์ชันเทียบกันตรง ๆ ไม่ได้

## 1. หลักการ 4 ข้อ

1. **Label สิ่งที่เอกสารระบุ ไม่ใช่สิ่งที่คุณอนุมานได้**
   เขียน Django แล้วเราเดาได้ว่าต้องรู้ Python — แต่ "เดาได้" ไม่ใช่ "ระบุไว้"
2. **"ไม่พบในเอกสาร" ≠ "ไม่มีคุณสมบัติ"** (charter §8.4)
   ต้องบันทึกแยกกัน และห้ามเขียนในช่องเดียวกัน
3. **Blind** — ห้ามดู profile ที่ generator ใช้สร้าง resume ก่อน label เสร็จ
4. **กำกวมแล้วบันทึกไว้ ห้ามเดาเงียบ ๆ** — เคสกำกวมคือข้อมูลที่บอกว่าคู่มือยังไม่ดีพอ

## 3. ขั้นตอนต่อ resume — ทำ 2 รอบ

### รอบที่ 1 — อ่านและจดด้วยคำของตัวเอง

อ่าน PDF แล้วจดทักษะที่เห็น **เป็นข้อความตามที่เอกสารเขียน** ยังไม่ต้องแปลงเป็น canonical id

> ทำไมต้องแยกเป็น 2 รอบ: ถ้าเปิด taxonomy แล้วมองหาว่าทักษะไหน "มีในรายการ"
> สายตาคุณจะถูกจำกัดโดยรายการนั้น และทักษะที่ taxonomy ยังไม่มีจะถูกมองข้ามเงียบ ๆ
> การจดด้วยคำของตัวเองก่อนจึงเป็นวิธีค้นหา **OOV skill** ที่ taxonomy ต้องเพิ่ม

### รอบที่ 2 — map เข้า canonical id

แปลงที่จดไว้เป็น id จาก taxonomy
- map ไม่ได้ → ใส่ใน `oov` พร้อมข้อความต้นฉบับ
- ไม่มั่นใจ → ใส่ใน `skills_uncertain` พร้อมเหตุผล

## 4. กฎ Label ทักษะ

### 4.1 สามหมวด

| หมวด | ความหมาย | นับใน F1? |
|---|---|---|
| `skills_stated` | เอกสารระบุชัดว่าผู้สมัครมี/เคยใช้ | ✅ นับ |
| `skills_uncertain` | เห็นเค้า แต่ตีความได้หลายทาง | ❌ ตัดออกจากทั้ง TP/FP/FN |
| `oov` | เป็นทักษะแน่ แต่ taxonomy ยังไม่มี | ❌ ไม่นับ · ใช้ปรับปรุง taxonomy |

### 4.2 🔴 ห้ามใส่ทักษะที่ได้จากการอนุมาน

เขียน Pandas → **ห้าม** ใส่ `python`
เขียน Django → **ห้าม** ใส่ `python`
เขียน React → **ห้าม** ใส่ `javascript`

การอนุมานเป็นหน้าที่ของระบบ และระบบต้องติดธง `inferred: true` แยกไว้
ถ้า label มีการอนุมานปนอยู่ ตัวเลข F1 จะให้รางวัลกับการเดา ซึ่งขัดหลักการข้อ 1

### 4.3 ตารางตัดสิน — ใช้เทียบเวลาติด

| ข้อความใน resume | label | เหตุผล |
|---|---|---|
| `Proficient in Python` | ✅ `python` | ระบุชัด |
| `Familiar with Docker` | ✅ `docker` | "familiar" ยังถือว่าระบุไว้ · ระดับความชำนาญเป็นเรื่องของ ranking ไม่ใช่ extraction |
| `Built REST APIs with FastAPI` | ✅ `rest_api`, `fastapi` | ระบุทั้งสอง |
| `Used pandas for data cleaning` | ✅ `pandas` เท่านั้น | **ห้าม**ใส่ `python` (§4.2) |
| `Currently learning Rust` | ❌ ไม่ใส่ | ยังไม่มี · เป็นความตั้งใจ |
| `Interested in Kubernetes` | ❌ ไม่ใส่ | ความสนใจไม่ใช่ทักษะ |
| `No experience with Java` | ❌ ไม่ใส่ | ปฏิเสธชัดเจน |
| `Coursework: Machine Learning, Statistics` | ✅ `machine_learning`, `statistics` | เอกสารระบุไว้ · ความหนักแน่นของหลักฐานเป็นเรื่องของ ranking |
| `JS` ในหัวข้อ Skills | ✅ `javascript` | บริบทชัด (อยู่ในหัวข้อทักษะ) |
| `R` เดี่ยว ๆ ไม่มีบริบท | ⚠️ `skills_uncertain` | ตัวอักษรเดียว ตีความได้หลายทาง |
| `SQL Server` | ✅ `sql_server` · **ไม่ใส่** `sql` | เป็นทักษะต่างตัว · `sql` เป็น related ไม่ใช่ alias |
| `AWS (S3, EC2)` | ✅ `aws`, `s3`, `ec2` ตามที่ taxonomy มี | ระบุครบ |
| `Team lead for 5 developers` | ✅ `leadership` | soft skill ที่ระบุด้วยหลักฐาน |
| ทักษะที่ปรากฏเฉพาะในข้อความ JD ที่ผู้สมัครคัดลอกมาใส่ | ❌ ไม่ใส่ | ไม่ใช่ทักษะของผู้สมัคร · ถ้าเจอเคสนี้ให้บันทึกไว้ เพราะเป็นกับดัก false positive ของระบบ |

### 4.4 คำย่อกำกวม

`R` `GO` `C` `SAS` `ML` `JS` `K8s` — ให้ดูบริบท

| บริบท | ตัดสิน |
|---|---|
| อยู่ในหัวข้อ Skills / Technical Skills | ตีความเป็นทักษะได้ |
| อยู่ติดกับ token เทคนิคที่รู้จัก (`R, Python, SAS`) | ตีความได้ |
| อยู่ในประโยคธรรมดา (`...go to market...`) | ❌ ไม่ใส่ |
| ตัดสินไม่ได้ | `skills_uncertain` + เหตุผล |

### 4.5 ⚠️ ห้ามใช้ pre-annotation กับ Tier B

อย่าให้สคริปต์เดาทักษะมาให้แล้วคุณแค่ติ๊กถูก/ผิด
คนมีแนวโน้มกดยอมรับสิ่งที่เครื่องเสนอ → เฉลยจะเอนไปทางระบบ →
F1 สูงขึ้นโดยที่ระบบไม่ได้ดีขึ้น

(Tier A ไม่มีปัญหานี้ เพราะ label มาจาก generator อยู่แล้ว)

> **ยืนยันจากภายนอก (เพิ่ม 2026-11-18):** ATS ตัวหนึ่งที่สำรวจมาใช้หลักเดียวกันในบริบทคนละเรื่อง —
> **ซ่อนผลประเมินของเพื่อนร่วมทีมไว้จนกว่าเราจะส่งผลประเมินของตัวเองก่อน**
> (`04-related-work.md` §5.3.2) · เหตุผลเดียวกันเป๊ะ: เห็นคำตอบของคนอื่นก่อนแล้วจะเอนไปตามนั้น
> → กฎข้อนี้ของเราไม่ได้ระแวงเกินเหตุ มันเป็นวิธีปฏิบัติที่คนทำระบบจ้างงานจริงใช้กัน
>
> **ขยายกฎให้ครอบคลุมตัวเราเองด้วย:** ตอน test–retest (§11) ต้องเก็บไฟล์รอบแรกไว้ที่อื่น
> ให้มองไม่เห็น ซึ่ง §11 เขียนไว้แล้ว · และตอน annotate ranking (§6) **ห้ามเรียงผู้สมัคร
> ตามคะแนนของระบบมาให้ดู** เพราะนั่นคือ pre-annotation ในรูปแบบของการจัดลำดับ

## 5. การศึกษา และ ประสบการณ์

### 5.1 การศึกษา

| ฟิลด์ | กฎ |
|---|---|
| `degree` | เลือกจากรายการปิดเท่านั้น: `high_school` · `vocational` · `bachelor` · `master` · `phd` |
| `field` | คัดตามที่เอกสารเขียน ไม่แปล ไม่ย่อ |
| `institution` | คัดตามที่เอกสารเขียน |
| `end_year` | ปีที่จบ · ถ้าเขียน "Expected 2027" ให้ใส่ 2027 และตั้ง `expected: true` |
| ไม่ระบุปี | ใส่ `null` · **ห้ามเดาจากอายุหรือจากปีที่เริ่มทำงาน** |

### 5.2 ประสบการณ์ทำงาน

- นับเฉพาะตำแหน่งที่มีนายจ้าง (รวมฝึกงาน และสัญญาจ้าง)
- **ไม่นับ** โปรเจคในวิชาเรียนหรือโปรเจคส่วนตัว → ไปอยู่ในส่วน `projects`
- วันที่: ความละเอียดระดับเดือน `YYYY-MM`
- `Present` → ใส่ `end: null` และ `current: true`
- ช่วงเวลาทับกัน (ทำ 2 งานพร้อมกัน) → บันทึกทั้งสองตามที่เขียน ไม่ต้องแก้ให้สวย

## 6. Job Requirement และ Ranking

### 6.1 Annotate job requirement

แยก 2 ชั้นให้ชัด:

| ชั้น | ความหมาย |
|---|---|
| `required_skills` | ขาดแล้วทำงานนี้ไม่ได้ |
| `preferred_skills` | มีแล้วดี ขาดแล้วยังทำได้ |

ถ้าข้อความ JD เขียนกำกวม (`familiarity with Docker is a plus`) → `preferred`
ถ้าเขียน `must have` / `required` → `required`
ถ้าแยกไม่ออก → บันทึกในช่อง note ของ job นั้น

### 6.2 Rubric เกรด 0–3

ให้เกรดต่อคู่ (ตำแหน่ง, ผู้สมัคร)

| เกรด | เกณฑ์ |
|---|---|
| **3** | มี `required` **ครบทุกตัว** และมีหลักฐานว่าเคย**ใช้งานจริง** (ปรากฏในประสบการณ์หรือโปรเจค ไม่ใช่แค่ในหัวข้อ Skills) |
| **2** | มี `required` ครบ แต่หลักฐานการใช้งานอ่อน (อยู่แค่ในรายการทักษะ) · **หรือ** ขาด `required` ไม่เกิน 1 ตัว แต่ที่เหลือมีหลักฐานแน่น |
| **1** | ขาด `required` ตั้งแต่ 2 ตัวขึ้นไป แต่ยังอยู่ในสายงานใกล้เคียง หรือมี `preferred` หลายตัว · **หรือ** ขาด `required` 1 ตัว **และ** ที่เหลือมีหลักฐานอ่อน (อยู่แค่ในรายการทักษะ) *(เพิ่มใน v1.2)* |
| **0** | ไม่มี `required` เลย หรือสายงานต่างกันสิ้นเชิง |

**ตารางตรวจความครบของ rubric (เพิ่มใน v1.2)** — ทุกช่องต้องมีเกรดเดียว ถ้าเจอเคสที่ลงช่องไหนไม่ได้ ให้บันทึกตาม §7

| ขาด `required` | หลักฐานแน่น (ใช้ในประสบการณ์/โปรเจค) | หลักฐานอ่อน (อยู่แค่ในรายการทักษะ) |
|---|---|---|
| 0 ตัว | **3** | **2** |
| 1 ตัว | **2** | **1** ← ช่องที่ v1.1 ไม่ได้ครอบ |
| ≥ 2 ตัว · สายใกล้เคียงหรือมี `preferred` หลายตัว | **1** | **1** |
| ทุกตัว · หรือสายต่างสิ้นเชิง | **0** | **0** |

⚠️ **ยังไม่ได้นิยาม (รอ pilot):** ถ้า required บางตัวมีหลักฐานแน่น บางตัวอยู่แค่ในรายการ
นับเป็นแน่นหรืออ่อน · และเส้นแบ่ง "สายใกล้เคียง" กับ "สายต่างสิ้นเชิง" ·
ระหว่างนี้ใช้คำถามตัดสินข้างล่าง และบันทึกทุกครั้งตาม §7

**เกณฑ์ตัดสินเวลาลังเลระหว่าง 2 เกรด:** ถามว่า "ถ้าเป็น HR จะเรียกคนนี้มาสัมภาษณ์ไหม"
→ เรียกแน่ = 3 · น่าจะเรียก = 2 · เรียกถ้าคนไม่พอ = 1 · ไม่เรียก = 0

### 6.3 🔴 เกณฑ์ที่ห้ามใช้เด็ดขาด

ห้ามให้สิ่งเหล่านี้มีผลต่อเกรด: **เพศ · อายุ · ชื่อและนามสกุล · สัญชาติ · รูปถ่าย · ศาสนา · สถานภาพสมรส · ที่อยู่**

⚠️ **ระวังชื่อสถาบันการศึกษาเป็นตัวแทนของฐานะทางสังคม** — ใช้ได้เฉพาะเมื่อ JD ระบุคุณวุฒิไว้จริง
และให้ใช้ที่ *ระดับวุฒิและสาขา* ไม่ใช่ *ชื่อเสียงของสถาบัน*

### 6.4 ช่อง `reason` บังคับกรอก

ทุกเกรดต้องมีเหตุผล 1 บรรทัด

ไม่ใช่ของประดับ — เวลา annotate รอบสองเพื่อวัดเพดานมนุษย์ (§11)
คุณจะได้เห็นว่าเหตุผลเดิมยังสมเหตุสมผลไหม และตอนทำ error analysis มันคือข้อมูลดิบ

## 7. กรณีกำกวม — ทำอย่างไร

1. ตัดสินใจไปตามที่คิดว่าเหมาะที่สุด **อย่าค้างไว้**
2. บันทึกในช่อง `notes` ของไฟล์นั้น ว่ากำกวมเพราะอะไรและตัดสินแบบไหน
3. เพิ่มแถวใน `docs/annotation-decisions.md`: ข้อความต้นฉบับ · การตัดสิน · เหตุผล · วันที่
4. ถ้าเคสแบบเดียวกันเจอครั้งที่ 3 → **เพิ่มเป็นกฎในคู่มือนี้** และขึ้นเวอร์ชัน

ไฟล์ `annotation-decisions.md` จะกลายเป็นคำตอบของคำถามสัมภาษณ์ว่า
"เจอข้อมูลกำกวมแล้วจัดการยังไง"

## 8. รูปแบบไฟล์

### 8.1 Label ต่อ resume — `dataset/labels/resumes/R-001.yaml`

```yaml
resume_id: R-001
annotator: korn
annotated_at: 2026-11-20
guidelines_version: 1
taxonomy_version: 1
minutes_spent: 14

contact:
  name: "Somchai Prasert"
  email: "somchai.p@example.com"
  phone: "+66812345678"

skills_stated:
  - python
  - sql
  - pandas

skills_listed_only:    # 🆕 ไม่บังคับ · ต้องเป็นสับเซตของ skills_stated
  - sql                #    = เจอเฉพาะในรายการทักษะ ไม่มีร่องรอยการใช้งาน

skills_uncertain:
  - id: docker
    reason: "เขียนว่า containerization ไม่ได้ระบุชื่อเครื่องมือ"

oov:
  - text: "Streamlit"
    note: "taxonomy v1 ยังไม่มี"

education:
  - degree: bachelor
    field: "Computer Science"
    institution: "Chiang Mai University"
    end_year: 2024
    expected: false

experience:
  - title: "Backend Developer Intern"
    employer: "Acme Co"
    start: 2023-06
    end: 2023-12
    current: false

projects:
  - name: "Expense tracker"
    skills: [python, sqlite]

not_found:          # ยืนยันว่าอ่านแล้วไม่มี
  - certifications
  - languages

notes: ""
```

**`not_found` สำคัญ** — แยก "อ่านแล้วไม่มี" จาก "ยังไม่ได้ label"
ถ้าไม่มีฟิลด์นี้ ไฟล์ที่ทำครึ่งทางจะดูเหมือนไฟล์ที่เสร็จแล้ว

> **🆕 `skills_listed_only` (เพิ่ม 2026-11-18) — ไม่บังคับ และไม่มีผลต่อ F1**
>
> **มันคืออะไร:** ทักษะที่เจอ *เฉพาะ* ในหัวข้อ Skills เปล่า ๆ โดยไม่ปรากฏในประสบการณ์
> หรือโปรเจคเลย · ยังนับใน `skills_stated` เต็ม ๆ ตามกฎ §4.3 (`Familiar with Docker` ก็ยังนับ)

### 8.3 สคริปต์ตรวจ (ต้องผ่านก่อนถือว่า label เสร็จ)

ตรวจว่า: skill id ทุกตัวมีใน taxonomy · ไม่มี id ซ้ำในไฟล์เดียว ·
id เดียวกันไม่อยู่ทั้งใน `stated` และ `uncertain` · `grade` อยู่ใน 0–3 ·
`degree` อยู่ในรายการปิด · resume ทุกใบใน Tier B มีไฟล์ label ครบ 1 ไฟล์ ·
ทุกตำแหน่งมีเกรดครบทุกผู้สมัคร ·
🆕 **`skills_listed_only` ทุกตัวต้องอยู่ใน `skills_stated`** ·
🆕 **`guidelines_version` ของทุกไฟล์ใน Tier B ต้องเป็นค่าเดียวกัน** (กันเฉลยคนละเวอร์ชันปนกัน ตาม §10)

## 9. ลำดับงาน annotate

```
1. annotate job requirement 6 ตำแหน่งก่อน   (~30 นาที)
2. pilot resume 5 ใบ → แก้คู่มือ             (§10)
3. annotate resume ที่เหลือ 25 ใบ
4. annotate ranking 6 × 30 = 180 คู่
5. รอ 14 วัน → test-retest 10 ใบ             (§11)
```

ทำ job requirement ก่อน resume เพราะ rubric ranking อ้างอิง `required_skills`
ถ้ายังไม่นิ่ง จะให้เกรดไม่ได้

## 10. Pilot — ห้ามข้าม

annotate **5 ใบแรก** แล้ววัด:

| วัดอะไร | เกณฑ์ตัดสิน |
|---|---|
| เวลาต่อใบ | > 20 นาที → พิจารณาสร้างหน้าช่วย label (ดูท้ายเอกสาร) |
| จำนวนเคสกำกวมต่อใบ | > 3 → คู่มือยังไม่ชัดพอ ต้องแก้ก่อนทำต่อ |
| จำนวนทักษะ OOV | เยอะ → taxonomy ยังแคบ ต้องขุดเพิ่ม |

**แก้คู่มือแล้วขึ้นเป็น v2 และ annotate 5 ใบนั้นใหม่ด้วยคู่มือใหม่**
label ที่ทำด้วยคู่มือต่างเวอร์ชันปนกันไม่ได้

เหตุผลที่ pilot สำคัญ: ถ้าลุย 30 ใบด้วยคู่มือที่ยังไม่นิ่ง
คุณจะเสียงาน 8–10 ชั่วโมงและต้องทำใหม่ทั้งหมด

## 11. Test–Retest (วัดเพดานมนุษย์)

1. เลือก 10 ใบจาก Tier B
2. รออย่างน้อย **14 วัน**
3. annotate ใหม่ **โดยไม่ดูของเดิม** (เก็บไฟล์เดิมไว้ที่อื่น)
4. คำนวณ: Jaccard / F1 ของเซตทักษะ (ตัวเองเทียบตัวเอง) และ Spearman ของเกรด ranking

ค่านี้คือ **เพดาน** ของระบบ ผลโมเดลต้องรายงานเทียบค่านี้ ไม่ใช่เทียบ 1.0

🔶 ถ้าหาคนที่สองมา annotate ได้แม้แค่ 10 ใบ ให้ใช้ค่าระหว่างผู้ annotate แทนทันที
เพราะน่าเชื่อถือกว่า test–retest ของคนเดียวอย่างชัดเจน

### 11.1 🔴 ถ้าผล retest ออกมาต่ำ ให้แก้ rubric ไม่ใช่โทษตัวเอง (เพิ่ม 2026-11-18)

| ผลที่ได้ | ตีความว่าอะไร | ทำอะไร |
|---|---|---|
| Jaccard ของเซตทักษะต่ำ | **คู่มือนี้** ยังไม่ชัด — น่าจะเป็น §4.3 หรือ §4.4 | เพิ่มแถวในตารางตัดสิน §4.3 แล้วขึ้นเวอร์ชันคู่มือ · annotate 10 ใบนั้นใหม่ |
| **Spearman ของเกรด ranking ต่ำ** | **rubric §6.2 แยกเกรดไม่คมพอ** | แก้ §6.2 ให้เกณฑ์แยกเกรดชัดขึ้น **แล้ว annotate ranking ใหม่ทั้ง 180 คู่** |

**ห้ามเดินหน้าด้วยเฉลยที่ตัวเองทำซ้ำไม่ได้** — ถ้าเฉลยไม่นิ่ง ทุกตัวเลขหลังจากนั้น
วัดความมั่วของเฉลย ไม่ได้วัดระบบ · และ 180 คู่คือราว 3 ชั่วโมง ซึ่งถูกกว่าการรายงาน
ตัวเลขที่เชื่อถือไม่ได้ไปทั้งโปรเจค

**หลักฐานว่าเรื่องนี้เกิดขึ้นจริงกับคนอื่น:** มีงานที่ให้คน 3 คน annotate การคัดกรอง resume
แล้วได้ Fleiss' kappa เพียง **0.167** จนผู้เขียนปฏิเสธที่จะถือว่า annotator คนใดเป็น
ground truth ⚠️ และฝั่ง IR มีรายงานว่าผู้ตรวจ 2 คนให้คะแนน relevance สเกล 0–4
ตรงกันเป๊ะเพียง **42%** ⚠️ (`04-related-work.md` §6.3)

→ **ค่าที่ต่ำไม่ได้แปลว่าคุณ annotate แย่ มันเป็นธรรมชาติของงานนี้**
สิ่งที่แยกโปรเจคที่เชื่อถือได้ออกจากโปรเจคที่เชื่อถือไม่ได้ คือการวัดมันออกมาแล้วรายงานตรง ๆ
ไม่ใช่การได้ค่าสูง
