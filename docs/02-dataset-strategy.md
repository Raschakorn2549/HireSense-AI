## 2. License ไม่ใช่สิ่งเดียวที่ต้องพิจารณา

### 2.1 🔴 License ที่ผู้อัปโหลดประกาศ ไม่ได้แปลว่าเขามีสิทธิ์ให้

CC0 และ MIT ข้างบนถูกประกาศโดย **ผู้รวบรวม** ไม่ใช่เจ้าของ resume
resume เหล่านั้นคนจริงเขียนและถูกดูดมาจาก livecareer.com และ LinkedIn
ผู้อัปโหลดไม่สามารถมอบสิทธิ์ที่ตัวเองไม่เคยถือได้

### 2.2 🔴 ลิขสิทธิ์กับข้อมูลส่วนบุคคลเป็นคนละเรื่อง

License เป็นเรื่อง **ลิขสิทธิ์** ไม่ใช่ฐานทางกฎหมายในการ **ประมวลผลข้อมูลส่วนบุคคล**

ชื่อ อีเมล และเบอร์โทรในไฟล์เหล่านั้นคือข้อมูลส่วนบุคคลภายใต้ PDPA ของไทย
การที่ไฟล์เป็น CC0 ไม่ได้ให้สิทธิ์เผยแพร่ข้อมูลนั้นต่อ

### 2.3 กฎการใช้งานข้อมูลภายนอก

| ทำได้ | ห้าม |
|---|---|
| ใช้ในเครื่องตัวเองเพื่อทดสอบความทนทานของ parser | redistribute ในรูปแบบใด ๆ |
| ขุดคำศัพท์ทักษะไปสร้าง taxonomy | commit เข้า git (รวม git history) |
| รายงาน **สถิติรวม** เช่น "parser อ่าน PDF จริงสำเร็จ 82%" | deploy ขึ้นเดโมสาธารณะ |
| อ้างอิง dataset ด้วย citation ตามเงื่อนไข CC-BY | แสดงเนื้อหา resume จริงในรายงานหรือสไลด์ |
| | ใช้ `datasetmaster/resumes` — การ์ดระบุว่าผสม real + synthetic แต่**ไม่มี provenance ระดับแถว** จึงรับประกันทั้งความเป็นส่วนตัวและการแยก train/eval ไม่ได้ |

## 3. 🔴 ข้อค้นพบที่กระทบแผนวัดผลโดยตรง

### 3.1 CareerCorpus ถูก anonymize แล้ว

หน้า Mendeley ระบุว่า **ชื่อ อีเมล และเบอร์โทรถูกแทนด้วย placeholder**

| ผลกระทบ | |
|---|---|
| ❌ | ใช้วัดเกณฑ์ "email / phone exact ≥ 95%" **ไม่ได้** เพราะข้อมูลที่จะวัดถูกลบไปแล้ว |
| ✅ | ใช้ทดสอบ layout และการสกัดทักษะได้เต็มที่ |
| ✅ | ปลอดภัยด้านความเป็นส่วนตัวมากกว่า Kaggle อย่างชัดเจน → **เป็นตัวเลือกแรกสำหรับ Tier C** |

### 3.2 Mehyaar มี label 5,029 ใบ แต่ไม่ใช้เป็น ground truth หลัก

**เหตุผลเชิงหลักการ:** ถ้าเอา label ของเขาเป็นเฉลย ตัวเลข F1 จะวัดว่า
"ระบบเราเห็นด้วยกับ taxonomy ของเขาแค่ไหน" ไม่ใช่ "ระบบเราแม่นแค่ไหน"
และการ์ดไม่ได้รายงานจำนวนผู้ annotate หรือค่าความสอดคล้องระหว่างผู้ annotate

**วิธีใช้ที่ถูกต้อง:**
1. แหล่งขุดคำศัพท์สร้าง taxonomy ← ประโยชน์หลัก
2. ตัวเลข "external agreement" รายงาน **แยกต่างหาก** พร้อมคำเตือน ห้ามปนกับ F1 ทางการ

### 3.3 CareerCorpus ให้เพดานมนุษย์

คะแนนจากผู้เชี่ยวชาญ 2 คน ที่ Pearson **0.35–0.89** เป็นหลักฐานว่า
งานประเมินผู้สมัครมีเพดานบนที่ต่ำ → ใช้อ้างอิงใน `01-evaluation-plan.md` §5.2

## 4. โครงสร้าง 3 Tier

แยกตาม **ที่มาของ label** ไม่ใช่แยกแค่ตามขนาด

| Tier | ชื่อ | ที่มาของ label | ขนาด | เผยแพร่ได้ |
|---|---|---|---|---|
| **A** | Development | input ของ generator (ฟรี) | **150** | ✅ |
| **B** | Evaluation | คน verify จาก PDF แบบ blind | **30** (+10 final holdout) | ✅ |
| **C** | Stress test | ไม่มี label | **50** | ❌ เก็บในเครื่องเท่านั้น |

### 4.1 Tier A — label ได้ฟรี ไม่ต้อง annotate

สร้าง resume จาก profile ที่มีโครงสร้าง → เรารู้อยู่แล้วว่าใส่ทักษะอะไรลงไป
ground truth คือ **input ของ generator** ไม่ใช่งาน annotate

**ข้อแลกเปลี่ยนที่ต้องยอมรับและบันทึก:** label ตรงกับการสร้าง 100%
→ ความแม่นบน Tier A **มองโลกในแง่ดีเกินจริงโดยธรรมชาติ** → ห้ามรายงาน

### 4.2 Tier B — ต้อง annotate แบบ blind

อ่าน **PDF ที่ render แล้ว** และ label สิ่งที่ตาเห็น โดย **ไม่ดู** input ของ generator
ถ้าดู = ยืนยันโน้ตตัวเอง ไม่ใช่การประเมิน

ของแถม: สิ่งที่ generator ใส่ไว้แต่อ่านจาก PDF ไม่เจอ = **ข้อมูลที่หายในขั้น render/extract**
ซึ่งเป็นผลการค้นพบที่มีค่าในตัวเอง ให้บันทึกไว้

### 4.3 Tier C — robustness เท่านั้น

ไม่มี ground truth → **ห้ามเคลม extraction F1** ตามกฎที่ตกลงไว้

metric ที่วัดได้โดยไม่ต้องมี label:

| metric | นิยาม |
|---|---|
| text extraction success rate | % PDF ที่สกัดข้อความออกมาได้ไม่ว่าง |
| section detection rate | % ที่ตรวจพบหัวข้ออย่างน้อย 1 หัวข้อ |
| encoding anomaly rate | % ที่มีอักขระเพี้ยน / mojibake |
| contact presence rate | % ที่หาอีเมลเจอ (CareerCorpus คาดว่าต่ำเพราะ anonymize) |
| crash / timeout rate | % ที่ parser ล้มหรือเกินเวลา |

ลำดับความสำคัญของแหล่ง: **CareerCorpus ก่อน** (anonymize แล้ว) → Kaggle เสริมถ้าต้องการ layout หลากหลายกว่า

## 5. การแบ่งชุด และการป้องกัน Leakage

| ความเสี่ยง | มาตรการ |
|---|---|
| ไฟล์ซ้ำข้ามชุด | manifest เก็บ SHA-256 ทุกไฟล์ + ชุดที่สังกัด · test ยืนยันไม่มี hash ซ้ำ 2 ชุด |
| template ทำให้ผลดูดีเกินจริง | **Tier A ใช้ T1–T3 · Tier B ใช้ T4–T5 ที่ไม่เคยใช้** |
| pool เดียวกันกระจายหลายชุด | ชื่อคน นายจ้าง ชุดทักษะ และ generator seed ต้องไม่ทับกันข้ามชุด |
| near-duplicate | TF-IDF cosine ทุกคู่ข้ามชุด · เกิน threshold → เอาออกจาก Tier B |
| เผลอใช้ eval ตอนพัฒนา | lockbox ตาม `01-evaluation-plan.md` §8.1 |

### 5.1 ทำไมต้องแยก template family ไม่ใช่แค่แยกไฟล์

ถ้า Tier A และ Tier B ใช้ template ชุดเดียวกัน parser จะเรียนรู้ **เทมเพลต** ไม่ใช่ **โครงสร้าง resume**
แล้วตัวเลขบน Tier B จะสูงอย่างหลอกลวง เพราะมันไม่ใช่ layout ใหม่จริง

การบังคับให้ Tier B ใช้ T4–T5 ทำให้ตัวเลขทางการสะท้อนความสามารถในการ generalize
ซึ่งเป็นสิ่งที่เราอยากรู้จริง ๆ

## 6. กลยุทธ์สร้างข้อมูลสังเคราะห์

### 6.1 Profile → Resume → PDF

```
profile (YAML มีโครงสร้าง)
   │  ชื่อ · ติดต่อ · การศึกษา · ประสบการณ์ · ทักษะ (canonical id) · โปรเจค
   ▼
renderer (เลือก template T1–T5)
   ▼
HTML → PDF
   │
   └──► ground truth ของ Tier A = ตัว profile เอง (ฟรี)
```

#### 🔴 เพิ่ม 2026-11-18 — generator ต้องสร้าง counterfactual pair ตั้งแต่แรก

`01-evaluation-plan.md` §11 เพิ่มงานวัดที่ 3 คือ counterfactual invariance
ซึ่งต้องมี resume **คู่** ที่เนื้อหาเหมือนกันทุกตัวอักษร ยกเว้นชื่อ คำนำหน้า และสรรพนาม

```
profile (YAML)
   │
   ├──► render ด้วย identity A  (ชื่อ/คำนำหน้า/สรรพนาม ชุดที่ 1)
   └──► render ด้วย identity B  (ชื่อ/คำนำหน้า/สรรพนาม ชุดที่ 2)
             │
             └──► คู่นี้มี profile_id เดียวกัน แต่ resume_id ต่างกัน
                  manifest ต้องมีคอลัมน์ counterfactual_of
```

**ทำไมต้องทำตอนนี้ ไม่ใช่ทำย้อนหลัง:** ถ้า generator ไม่แยก identity ออกจาก profile
ตั้งแต่ต้น การมาสร้างคู่ทีหลังต้องรื้อ profile pool ทั้งชุด และ resume ที่ render แล้ว
จะใช้ไม่ได้ (เพราะชื่อฝังอยู่ในเนื้อหา) · ต้นทุนตอนนี้คือการแยกฟิลด์ `identity`
ออกจาก `profile` ในสคีมา ซึ่งแทบไม่มีราคา

**ตำแหน่งของ identity ในเอกสาร (เพิ่ม 2026-11-18 รอบ 2):** ชื่อ คำนำหน้า สรรพนาม
และอีเมล ต้องอยู่ใน **บล็อกหัวกระดาษเท่านั้น** · สรรพนามเขียนในรูป `(she/her)` ต่อท้ายชื่อ ·
generator **ห้าม** ใส่ชื่อหรือสรรพนามในส่วนอื่นของ resume (เช่นย่อหน้า summary)
เหตุผลอยู่ใน `01` §11.6

**ขอบเขตที่ตกลงไว้:** เปลี่ยนแค่ **ชื่อ-นามสกุล · คำนำหน้า · สรรพนาม**
· **ห้ามเปลี่ยน** อีเมล (เพราะอีเมลมักมีชื่ออยู่ในนั้น ให้ใช้รูปแบบ `firstname.l@example.com`
ที่เปลี่ยนตามชื่อโดยอัตโนมัติ) · ที่อยู่ ชื่อสถาบัน และปีจบ **ยังไม่เปลี่ยน** ในรุ่นแรก
(เรื่องรอตัดสิน `01` §10 ข้อ 6)

**จำนวน:** สร้างคู่เฉพาะใน **Tier A** ก่อน (ไม่กิน budget annotate เลย เพราะ label มาจาก generator)
→ ถ้า Tier A มี 150 ใบ ให้ 20 ใบในนั้นมีคู่ของตัวเอง = 10 คู่ · **Tier B ไม่ต้องมีคู่**
เพราะ counterfactual ไม่ต้องใช้เฉลยมนุษย์เลย — มันเทียบผลของระบบกับผลของระบบเอง

#### เรื่อง renderer: ยังไม่ตัดสิน แต่มีตัวเลือกที่คนอื่นใช้แล้ว

| ทาง | ใครใช้ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **HTML → PDF** (weasyprint / pdfkit) | ResumeBench ใช้ pdfkit สร้าง 2,500 ใบ ⚠️ | คุม layout หลายคอลัมน์ได้ง่ายด้วย CSS · ทำ template ได้เร็ว | ต้องพึ่ง binary ภายนอก (wkhtmltopdf) |
| **reportlab** | `04-related-work.md` §5.3.5 ใช้สร้าง PDF fixture ในเทส | เป็น Python ล้วน ไม่ต้องมี binary · **สร้าง PDF ที่เป็นภาพล้วนได้ สำหรับเทส OCR** | เขียน layout หลายคอลัมน์ยากกว่า |
| **Playwright + Edge ที่ติดตั้งอยู่แล้ว** (เพิ่ม 2026-11-18 รอบ 2) | — | engine เดียวกับเบราว์เซอร์ที่คนใช้ export resume จริง · คุมสองคอลัมน์ด้วย CSS · **ไม่ต้องดาวน์โหลด Chromium ~150MB** (สำคัญเพราะเน็ตที่ใช้พัฒนาวัดได้ ~24 KB/s) · ถ่ายภาพหน้าได้ → ใช้ทำ PDF ภาพล้วนได้ด้วย | ผล render ผูกกับเวอร์ชัน Edge ที่อาจอัปเดตตัวเอง → **ต้องบันทึกเวอร์ชันเบราว์เซอร์ใน manifest** · เวอร์ชันตอนตัดสินใจ: Edge 157.0.4341.60 |

→ **ตัดสินแล้ว 2026-11-18: ใช้ Playwright สั่ง Edge ที่ติดตั้งอยู่แล้ว เป็นตัวสร้าง PDF หลักของ T1–T5**
(ไม่ใช้ pdfkit เพราะต้องพึ่ง wkhtmltopdf · ไม่ใช้ weasyprint เพราะต้องลง GTK แยกบน Windows)

→ **PDF ภาพล้วน: ตัดสินแล้ว — Edge ถ่ายภาพหน้า + Pillow บันทึกเป็น PDF · ไม่ใช้ reportlab**
ผลทดลอง: ตัวอ่านทั้ง 3 ตัวดึงข้อความได้ 0 ตัวอักษร ตามที่ต้องการ (§6.5)

### 6.2 ความหลากหลายที่ต้องจงใจใส่

| มิติ | ต้องมี |
|---|---|
| **layout** | คอลัมน์เดียว · สองคอลัมน์ · มีตาราง · มี header/footer · มีไอคอน |
| **ความยาว** | 1 หน้า และ 2+ หน้า |
| **สายอาชีพ** | Backend · Data Analyst · ML Engineer (+ 3 ตำแหน่งเพิ่มถ้าใช้ 6 ตำแหน่ง) |
| **ระดับประสบการณ์** | นักศึกษาฝึกงาน · จบใหม่ · 2–5 ปี |
| **ระดับความตรงกับตำแหน่ง** | ตรงมาก · ตรงบางส่วน · ไม่ตรง · **ตรงแบบกำกวม** (สำคัญที่สุด — เป็นเคสที่แยกระบบดีจากระบบแย่) |
| **ความสะอาดของข้อความ** | เขียนดี · เขียนรวบรัด · มีคำพิมพ์ผิด · ปนคำย่อ (`JS`, `K8s`, `ML`) |
| **เคสขอบ** | ไม่มีอีเมล · มี 2 เบอร์ · วันที่รูปแบบแปลก · ประโยค "ต้องการเรียนรู้ Rust" (ต้อง **ไม่** นับเป็นทักษะ) |
| **เคสโจมตี** (เพิ่ม 2026-11-18 · ปรับตามผลทดลอง 2026-11-24) | **ฝังข้อความที่มองไม่เห็นใน PDF** ใส่คำว่า `Python Kubernetes AWS` ไว้ · ระบบต้อง **ไม่** นับ · ใช้ **3 เทคนิคที่ Edge สร้างได้จริง**: ตัวอักษรสีขาว · สี `transparent` · ขนาด 1px (§6.5) · เทคนิค **ขนาด 0** และ **นอกขอบกระดาษ** Edge ตัดทิ้งตอนสร้าง PDF จึง**ยังไม่ได้ทดสอบ** — เป็นข้อจำกัดที่ต้องเขียนในรายงาน |
| **เคส OCR** (เพิ่ม 2026-11-18) | **PDF ที่เป็นภาพล้วน** 2–3 ใบ (สกัดข้อความไม่ได้เลย) เพื่อทดสอบ OCR fallback |
| **counterfactual** (เพิ่ม 2026-11-18) | 10 คู่ใน Tier A ที่ต่างกันแค่ชื่อ/คำนำหน้า/สรรพนาม (ดู §6.1) |

> **เพิ่ม 2026-11-18 — หมุดเทียบว่าความหลากหลายระดับไหนถือว่าพอ**
>
> ชุดข้อมูลที่ตีพิมพ์จริงใช้สเกลประมาณนี้ (`04-related-work.md` §2.1–2.2):
> ResumeBench = 2,500 ใบ / **50 template** / 30 สายอาชีพ · SynthResume = 2,994 ใบ
> ครอบคลุมทั้ง layout คอลัมน์เดียวและหลายคอลัมน์ · และ SynthResume ประมาณว่า
> **resume ราว 20% ใช้ layout ที่อ่านเรียงบรรทัดตรง ๆ ไม่ได้**
>
> ของเรามี **5 template** — น้อยกว่า 10 เท่า **และนั่นยอมรับได้** เพราะเราวัด generalize
> ด้วยการกัน T4–T5 ไว้ให้ Tier B (§5.1) ไม่ใช่ด้วยจำนวน
> **แต่ตัวเลข 20% เป็นข้อผูกมัด:** ถ้า T1–T5 ของเราเป็นคอลัมน์เดียวทั้งหมด
> เราจะวัดไม่เจอความล้มเหลวที่พบจริงบ่อยที่สุด → **ต้องมีอย่างน้อย 1 template
> ที่เป็นสองคอลัมน์จริง และอย่างน้อย 1 ใน T4–T5 ต้องเป็นแบบนั้น**

### 6.5 ผลทดลอง 01 — renderer check (2026-11-24)

สคริปต์และผลดิบ: `experiments/01-renderer-check/` · Edge 157.0.4341.60 · Playwright 1.65.2

**ก) PDF สองคอลัมน์ — ตัวสร้างไม่ทำข้อความหาย แต่ตัวอ่านให้ลำดับต่างกันมาก**

| ตัวอ่าน (ค่าเริ่มต้น) | บรรทัดที่ปนสองคอลัมน์ | สลับคอลัมน์ | ลำดับหัวข้อ |
|---|---|---|---|
| pdfplumber (pdfminer) | **5** | 15 ครั้ง | ปนกัน |
| pypdfium2 (PDFium) | 0 | 1 ครั้ง | ถูก |
| pymupdf (MuPDF) | 0 | 1 ครั้ง | ถูก |

⚠️ ผลเบื้องต้นจาก **1 layout** เท่านั้น ยังไม่ใช่การเลือก parser · PDFium กับ Chromium มาจากค่ายเดียวกัน
อาจอ่าน PDF ที่ Edge สร้างได้ดีเป็นพิเศษ → ต้องยืนยันกับ Tier C ใน Phase 2 (§9)

**ข) ข้อความที่มองไม่เห็น — 3 ใน 6 เทคนิคถูก Edge ตัดทิ้งตอนสร้าง PDF**

| เทคนิค | อยู่ในไฟล์ PDF | สิ่งที่ตัวอ่านเห็น |
|---|---|---|
| สีขาว | ✅ | สี `[1,1,1]` → ตรวจด้วยสีได้ |
| `color: transparent` | ✅ | 🔴 สีรายงานเป็น **ดำ** `[0,0,0]` → **ตรวจด้วยสีไม่ได้** |
| ขนาด 1px | ✅ | ขนาด 0.75pt → ตรวจด้วยขนาดได้ |
| ขนาด 0 · นอกขอบกระดาษ · `opacity: 0` | ❌ ถูกตัดทิ้ง | ไม่มีอะไรให้ตรวจ |

ผลต่อ Phase 2: ตัวป้องกันที่ดูแค่สีตัวอักษรจะพลาดเคส `transparent` ·
ตัวป้องกันที่ใช้ได้กับทุกเคสต้อง render หน้าเป็นภาพแล้วตรวจว่าตำแหน่งข้อความมีหมึกจริงหรือไม่

**ค) PDF ภาพล้วนด้วย Pillow** — 163 KB · ตัวอ่านทั้ง 3 ตัวได้ 0 ตัวอักษร → ใช้ได้

**ง) license** — PyMuPDF 2.1 ยืนยันเป็น **AGPL-3.0** และพ่วง onnxruntime (~17 MB) ·
เก็บไว้ใช้ทดลองในเครื่อง **ไม่ใส่ใน requirements**

ทุกไฟล์ต้องมีแถวใน `manifest.csv`

```csv
file_id,sha256,tier,template,source,license,added_at,profile_id,counterfactual_of,role,renderer
R-001,3f2a...,A,T1,synthetic,internal,2026-11-20,P-001,,eval,playwright-1.65.2/msedge-157.0.4341.60
R-002,7b4c...,A,T1,synthetic,internal,2026-11-20,P-001,R-001,eval,playwright-1.65.2/msedge-157.0.4341.60

```

> **เพิ่ม 3 คอลัมน์ 2026-11-18:**
> · `profile_id` — resume สองใบที่มาจาก profile เดียวกันต้องมีค่านี้เท่ากัน
> (ใช้กัน leakage ด้วย: profile เดียวกันห้ามกระจายข้าม tier ตาม §5)
> · `counterfactual_of` — ชี้ไปยัง resume ต้นทางของคู่ (ว่างถ้าไม่ใช่คู่)
> · `role` — `eval` / `smoke` / `stress` · **ไฟล์ `role: smoke` ห้ามเข้าการคำนวณ metric
> ทุกตัวในรายงาน** (§6.4)

สคริปต์ตรวจต้องยืนยัน: ไม่มี `sha256` ซ้ำข้าม tier · ทุกไฟล์ใน `pdf/` มีแถวใน manifest ·
ไฟล์ tier C ไม่มีอันไหนอยู่นอก `raw/` ·
**ทุกแถวที่มี `counterfactual_of` ต้องมี `profile_id` ตรงกับไฟล์ที่ชี้ไป** ·
**ไม่มีไฟล์ `role: smoke` อยู่ใน Tier B** ·
**ทุกแถวที่ `role: smoke` ต้องมีช่อง `tier` ว่าง** (เพิ่ม 2026-11-18 รอบ 2 — smoke ไม่ใช่ tier ใด ตาม §6.4)
